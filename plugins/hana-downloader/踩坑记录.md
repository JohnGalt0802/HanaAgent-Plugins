## 四象限实测记录

| 工况 | 操作链 | 关键结果 | 结论 |
|---|---|---|---|
| 1 回合内完成 | download-file → 同回合 wait | wait 返回 done（16.6KB / 16.6KB） | ✅ |

- 占位注册依赖 wait 快照（v0.5.7 起“创建时不注册”）：离场后能自动唤醒的前提，是离场前调过 wait 且任务未完成（wait 快照提示“占位已续注册”）。

- 顺带：一次 URL 404（typescript 5.10.2 不存在）→ 任务 failed → 也正常走投递路径（state=failed）。

# 踩坑记录：0.712.5 插件工具缺 sessionPermission 被拒（wait 不可用）（2026-08-27）

日期：2026-08-27
状态：已修复 ✅（待重载插件生效）
版本：0.5.9

## 症状

另一个会话报告「download-wait 现在不可用了」，调用报 `Tool invocation resolver rejected an unknown action or invalid target`。

## 根因

0.712.5 宿主要求插件工具必须声明 `sessionPermission`，否则 resolver 判 invalid target 拒绝。

宿主判定逻辑（bundle/index.js）：
```js
function U7e(e) { const t = e?.toolSessionPermission || e?.sessionPermission; return t && typeof t == "object" ? t : null; }
function H7e(e) { return e ? e.readOnly === !0 || typeof e.kind == "string" || e.auto === "allow" || e.auto === "review" : !1; }
// 工具无 sessionPermission → U7e 返回 null → H7e(null)=false → resolver 拒绝
```

对比插件四个工具：
- `download-file.js`：有 `{kind:"external_side_effect"}` → 可用
- `download-command.js`：有 `{kind:"external_side_effect"}` → 可用
- `download-wait.js`：**无** → 被拒（这就是“wait 不可用”）
- `download-cancel.js`：**无** → 被拒

旧版 0.686.15 不强制，所以 wait/cancel 一直没声明也能用；0.712.5 变严格后显形。

## 修复

- `tools/download-wait.js`：加 `export const sessionPermission = { kind: "read" };`（查询/守望只读）
- `tools/download-cancel.js`：加 `export const sessionPermission = { kind: "external_side_effect" };`（取消有副作用，与 file/command 一致）

两者语法已过 `node --check`。

## 关键教训

1. **插件工具必须带 sessionPermission**。0.712.5 起是硬校验，不是可选项。
2. **工具元数据在插件 onload 时固化**：改 tools 文件后，社区槽插件需重启 hana-server（`reloadPlugin` 只对 dev 槽生效）或开新会话才生效；当前会话不认新 sessionPermission。
3. 判定规则：`H7e` 要求 `readOnly:true` 或 `kind` 为字符串或 `auto: allow|review`。只读工具用 `{kind:"read"}`，副作用工具用 `{kind:"external_side_effect"}`。

# 踩坑记录：0.712.5 聊天流卡片被锁死 400px 宽（2026-08-27）

日期：2026-08-27
状态：已修复 ✅
版本：0.5.8

## 症状

宿主升级到 0.712.5 后，聊天流里的下载进度卡片**能正常显示**（进度条、百分比、按钮都在），但**宽度被锁死在 400px**，右侧留一大片空白，不再跟随聊天区宽度。

## 根因

`app/card.js` 的 `reportSize()` 一直在上报 `payload: { width: 400, height: h }`。

0.712.5 的 renderer（`artifacts\renderer\0.712.5\assets\SendButton-D9UnTlPv.js`）里：

```js
function ou(slot, next, cur, viewportH){
  if(slot === "card"){
    const w = next.width  !== undefined ? Math.max(50, next.width)  : cur.width;   // Zl = 50
    const h = next.height !== undefined ? Math.max(30, next.height) : cur.height;  // Ql = 30
    return { width: w, height: h };
  }
  // page slot 才 clamp 到 viewport
}
```

而真身渲染组件 `wd` 把 size.width **直接当卡片最大宽度用**：`maxWidthPx: g.width ?? void 0`。

所以插件报 `width:400` → `maxWidthPx=400` → 卡片锁死 400px。旧版宿主忽略 width，这个 bug 一直潜伏着，直到 0.712.5 才显形。

## 修复

`app/card.js` 的 `reportSize()` **只报 height，不报 width**：

```js
PARENT.postMessage(
  { protocol: "hana.plugin.ui", version: 1, kind: "event", type: "ui.resize", payload: { height: h } },
  HOST_ORIGIN
);
```

省略 width 后 `next.width === undefined` → 宿主用 `cur.width`（未设即 undefined）→ `maxWidthPx` 为 undefined → 卡片自然铺满聊天区。

**不需要重启 Hana**：`routes/download.js` 每次请求都重读 `app/card.js`，改完发起新下载即生效。

## 关键教训

1. **card slot 下绝不上报 width**。高度随便报（无上限，只有 30px 下限），宽度交给宿主。
2. **两个补丁可以退役了**：0.712.5 官方原生支持聊天流内嵌 iframe（`pd()` 接受 `webview`/`iframe`，走 `wd` 真身渲染）+ 内容驱动高度（card slot 无高度上限）。0.679.3 的 `Bn` 内嵌补丁、0.686.15 的 `i!==card&&` 高度补丁都不用再打。详见 `D:\HanakoWorks\_tools\hana-host-patches\PATCHES.md`。
3. **minified 产物里判断协议有没有消费方，不能只 grep 字面量**。`ui.resize` 的消费方写作 `we.UI_RESIZE`，字面量只存在于协议定义文件，按字面量搜会误判成"协议未接线"。要跟到常量名再搜一轮。
4. **看对目录**：Electron 实际加载 `artifacts\renderer\<版本>\`，不是 `artifacts\server\<版本>-win32-x64\desktop\dist-renderer\`。两套构建哈希不同。
5. `details.card` 的 `pluginId` 由宿主自动注入（`wH()`：`r.details.card && t && !r.details.card.pluginId && (...)`），插件不必自己填。

## 2026-08-24 deferred 占位断链：notifyWhenDone 只 resolve 不 register（v0.5.0 已修复 ✅）

### 症状
Agent 调 `download-wait(notifyWhenDone=true)` 后收束回合，下载完成（tasks.json state=done）但**永远不唤醒**。
会话 jsonl 实锤：agent 每一步都对（22:40 调 notifyWhenDone，明确说"后台通知已注册"），23:09 下载完成，无唤醒。

### 根因（宿主 bundle 实证，v0.681.5）
- 宿主 deferred 协议：`deferred:register`（注册占位，必需 sessionId/sessionPath）→ `deferred:resolve`（按 taskId 解析投递）。
  解析时**占位不存在 → 整个分支跳过，什么都不发生**（bundle line 150171）。
- 插件 index.js 只调了 resolve（onFinal 里），**全插件 grep 不到任何 register** → 占位从未建立 → resolve 空转，
  `.catch(()=>{})` 吞掉错误，静默失败。文档/工具描述里"注册后台通知"是虚假承诺。
- 宿主 bundle 里搜不到 `notifyWhenDone` 字样：宿主不认识这个参数，不会自动注册。
- 宿主内置机制（media/subagent/workflow）全部显式调 register——第三方插件要自注册。

### 同类断链
- 停滞通知（taskId:stall）同样只 resolve 不 register → 停滞也从不投递。

### 修复（v0.5.0）
- 创建任务时自动 register（download-file/command 内调 registerDeferred），不依赖 agent。
- 终态必投递（onFinal resolve）+ onload 对遗留终态任务幂等兜底（覆盖重启缝隙）。
- onStall 动态 register+resolve taskId:stall 占位（成对完成，无幽灵）。
- 宿主无"按任务取消占位"API（只有 register/retry/resolve/fail/abort，abort 会误报中止）→ 终态必投递，
  agent 已消费时投递冗余但无害（result 带 consumedByWait 标记识别）。
- 修改需重启 hana-server 生效（lib 模块缓存，dev reload 无效）。

### 教训
1. **host 协议先摸清再写通知逻辑**：只实现 resolve 端、不实现 register 端 = 空转轮子，文档承诺的"通知"根本不落地。
2. **bus 请求的失败被 .catch 吞掉时，永远无法发现断链**——onload 兜底 + 幂等 resolve 是安全网。
3. 宿主 bundle（artifacts/server/*/bundle/index.js）可 grep 实证协议实现，minified 可读。

## 2026-08-21 v0.2.3 阶段踩坑（下载管理器/explorer/高度）

### 坑1：explorer 打开文档文件夹（execFile 转义内嵌引号）
- 现象：打开/打开文件夹按钮弹的是“文档文件夹”（explorer 默认位置），不是目标路径
- 根因：`execFile("cmd.exe", ["/c", 'explorer.exe "C:\\Users\\John Galt\\..."'])` 时，**Node 默认对含空格+内嵌引号的参数自动加引号并转义内部引号为 `\"`** → cmd 收到错乱引号 → explorer 参数被截断 → 无参启动 → 打开文档
- 修复：加 `windowsVerbatimArguments: true` → Node 不转义引号，原样传给 cmd → explorer 收到完整路径
- 教训：execFile/exec 的 args 数组在 Windows 会按 CommandLineToArgvW 自动 quoting，内嵌引号会被转义；参数含引号时用 windowsVerbatimArguments 控制

### 坑2：卡片高度“自己变高”（body.scrollHeight 被宿主 iframe 拉伸）
- 现象：点击收起/展开后一秒内正常，下一秒被撑到大高度+下方大空白
- 根因：宿主给插件 iframe 的 body/html 注入 `height:100%` → `document.body.scrollHeight` 被拉成 iframe 高度（600）→ reportSize 报 600 → 宿主设 600 → 大空白。实测 body 设 height:100% 后 bodyScrollH=1036（视口），但 `.dl` 本体 offsetHeight=45 免疫
- 修复：reportSize 用**卡片本体 `.dl` 的 offsetHeight + body padding**（任何容器 height:100% 都拉不垮它）→ 折叠 61/展开 173/收起 61 永远贴合
- 教训：宿主 iframe 高度管理会注入 height:100% 给 body；报高不能用 body.scrollHeight（被污染），要用内容容器/本体

### 坑3：manager 行菜单“打开所在文件夹”失效（closeRowMenu 清空 rowMenuTask）
- 现象：manager 卡片行菜单“打开所在文件夹/打开文件”点了没反应
- 根因：`opt.onclick = function(){ closeRowMenu(); if(rowMenuTask) reveal(rowMenuTask); }` —— **closeRowMenu() 先把 rowMenuTask 置 null** → `if(rowMenuTask)` 恒 false → reveal 永不执行
- 修复：onclick 里**先存局部变量 `var t = rowMenuTask` 再 closeRowMenu 再用 t**
- 教训：函数内先清状态再判断同一状态 = 经典 bug；先快照再清理

### 坑4：cmd /c 命令注入面（老哥复核揪出）
- 现象：explorer 参数含 `&`/`|` 时可能被 cmd 拆成多条命令（`a&calc&b.zip` → 执行 calc）
- 修复：cmd /c + 双引号 + `^` 转义 `&|^%<>"!`（命令边界/重定向/转义符/变量展开全覆盖）
- 教训：cmd 的 `&|<>^%` 是命令分隔符/元字符，路径进 cmd 必须转义或参数化；经 cmd 层必然有注入面，需专门防护

### 坑5：spawn explorer.exe 直传 exit 1（explorer 自解析参数）
- 现象：`spawn("explorer.exe", ["/select,"+path])` 返回 exit 1（explorer 无视 CommandLineToArgvW，含空格参数自解析截断）
- 修复：必须经 `cmd /c` 包引号（explorer 才收到完整路径）

### 坑6：push 网络问题（HTTP/2 直连被拒 + 明文 token）
- 现象：git push 偶发 non-fast-forward 拒绝/认证失败/连接重置（TUN 环境）
- 根因：Clash TUN 环境 HTTP/2 POST 被干扰；git remote URL 里曾明文硬编码 token（违反安全）

- 教训：TUN/代理环境 git push 用 HTTP/1.1 + 显式 refspec 最稳；token 绝不能硬编码进 remote URL

### 坑8：会话内快速完成的下载不应投递 deferred（注册时机后移为「收束前续状态」）
- 现象（2026-08-25 用户指出）：快下载在创建会话结束前就完成（如 v056-node.zip 30s 内 done），主会话仍活着能直接看到结果，却收到 deferred 唤醒通知（consumedByWait: false）
- 根因：v0.5.4 起的「创建即注册占位 + 终态必投递」没有区分「Agent 是否已在本轮拿到结果」——会话内完成的任务收束后仍被异步唤醒，纯属噪音。宿主 IPC 无会话/turn 状态查询（21 协议仅 deferred/task），插件无法判定「当前轮次活跃」，「等回查/延迟复查」类方案在 Agent 干别的（回查排后）时也会漏
- 修复（v0.5.7 定稿）：**注册时机后移——创建时不注册，download-wait 快照在「任务未完成」时自动续注册**（Agent 收束前的最后动作；旧版 v1.6.7 notifyWhenDone 即此语义）。会话内完成（wait 快照到终态）→ 不注册 → 不投递；收束后完成 → 续的占位 resolve 投递唤醒。终态后延迟 5s 复查兜底窄间隙（续注册后 Agent 又回查拿到终态 → wait 消费 → 跳过）。wait 消费会取消复查定时器（markConsumedByWait → clearTimeout _resolveTimer）
- 教训：deferred 的投递语义是「唤醒收束后的会话」。注册时机应由 Agent 主动（收束前续状态），而非任务创建时自动——创建即注册把「会话内完成」和「收束后完成」混为一谈，才是噪音的源头

- 演进：v0.1.x/v0.2.2 用 `body.scrollHeight`（被 height:100% 污染报 600）→ d3ff5bb 改 `#dl-root.scrollHeight`（免疫，但少 padding）→ 26a35c3 补 padding → d67494c 最终用 `.dl.offsetHeight + padding`（绝对免疫）
- 教训：报高元素选最底层卡片本体；每换一次都要实测宿主 iframe 污染场景


### 坑9：为了「不漏通知」改回创建即注册，反而造成「大批重复通知」（v0.6.0→v0.6.3 弯路）
- 现象（2026-08-26~27）：一个下载任务在会话内完成，agent 收束后不该收到唤醒，却收到一条 deferred 通知（consumedByWait:false）。若 agent 一口气下 10 个会话内完成的小任务，会收到 10 条重复消息 = 10 次 API 调用 + 工作区间被塞满 + 10 次会话占用，代价远超「漏一条」。
- 根因：v0.6.0 为修 auto-fast-done 的「快下载漏通知」把 v0.5.7 的「创建不注册、wait 续注册」改成「创建即注册占位」。占位一创建，任务终态就投递；而「会话内完成」的任务 agent 明明在场看得到，根本不需要异步唤醒。于是大批会话内完成的任务被当成「该唤醒」全部投递，重复消息爆发。
- 走过的弯路（都验证失败）：
  1. 方案 Y（turn 感知）：插件订阅宿主 turn_start/turn_end 判断「任务终态时是否在回合内」，回合内静默/回合外投递。explorer 逆向 host bundle 结论「ctx.bus.subscribe 能订阅 turn 事件，零改动」——但实测 bus.subscribe 回调 0 触发（插件 onload 成功但收不到任何事件），explorer 只从代码形态推断没实测宿主是否真把 turn 事件喂给插件。方案不可行。
  2. 方案 X（宿主 suppressDelivery）：patch host bundle 的 MCt 加 deferred:suppress handler 转发 suppressDelivery，wait 已消费时灭占位。插件侧调用成功（探针 confirmed），但宿主投递器 class ZUt 的 this.store 与 MCt 的 t 疑似不是同一实例，deliverySuppressed 写进去投递读不到，还是投。深挖 store 一致性要动宿主核心、风险高收益低。
- 正解（回归 v0.5.7 后注册）：占位只在「agent 收束前确认任务未完成」时由 wait 快照续注册。会话内完成 → 无占位 → 不投递（修掉重复）。收束后完成 → 续的占位 → 投递唤醒。代价只是「agent 不规范（不调 wait 就收束）」时可能漏一条，但漏 1 ≤ 重复 10 的代价，且正常 agent 工作流（收束前调 wait）不漏。
- 教训：
  1. 机制设计要从「真实使用场景的放大后果」出发：单任务「双投」看似无害，放大到「10 个并发会话内完成的小任务」就是灾难。评估时用「会不会批量放大成几十条」这个标尺，而不是单个边缘 case 的善恶。
  2. 别用「解决 A 问题的方案」引入「B 类更严重问题」：v0.6.0 为修「漏」改成创建即注册，却引入了「重复爆发」这个更糟的病。改机制前先问一句「会不会把一种小毛病放大成另一种大毛病」。
  3. 逆向他人的编译产物做集成方案，必须实测验证关键前提，不能只相信静态推导（explorer 说「零改动可用」但实测收不到事件）。凡是「接入宿主内部能力」的方案，先做一次最小探针实测，再决定投入。
  4. 别为一个「方向无害的冗余」去动宿主核心 store 一致性——收益低、风险高、牵一发动全身。能不动宿主就不动。
  5. 用户点破了盲区：核心需求是「不重复通知」，不是「绝不漏」。要跳出局部 bug，回到需求本身重新权衡。

### 坑10：「2秒复查竞态」——后注册下仍会偶发「已消费仍投递」，且无法根治（v0.6.4 + 实测判死）
- 现象（2026-08-27 复现）：后注册方案下，`download-file(限速) → wait快照(running,续注册占位) → cancel → wait拿终态 → 收束`，收束后**仍收到一条重复投递**（`state=canceled`, `consumedByWait:false`）。用探针定位，任务终值 `consumedByWait=true`，但投递消息却是 `false`。稳定复现：`006aae13`、`b8e084cd` 均双投，`843fdf24` 偶发不投（一次成功）。
- 根因：**时序竞态**。任务进入终态(T0)时，`onFinal → resolveDeferred` 设一个「2秒复查闹钟」（定在 T0+2s 触发）。同时 agent 收束前调 wait 拿终态 → `markConsumedByWait`（写 consumed=true + `clearTimeout(_resolveTimer)`）。两者是异步竞速：
  - **wait 快**（2秒内 markConsumed）→ clearTimeout 成功按掉闹钟 → 复查不触发 → 不投递（`hadTimer=true`，本次 `843fdf24` 正确）。
  - **wait 慢**（网络/LLM推理/工具调度拖过 T0+2s）→ 闹钟先响，读 `consumedByWait` 还是 false → 先投递 → wait 之后才 markConsumed → 消息已发，重复。
- 关键理解：这个 2 秒窗口**同时是「去重复的宽容期」和「投递的触发时刻」**。拉长窗口只会让「该投递的正确唤醒」跟着延迟，不会只消灭重复；而且治标不治本（wait 比窗口还慢照样重复）。真正该拦掉的重复，就这样在竞态里漏出来了。
- 最后三次实测（v0.6.5 probe，全部判死「纯插件侧根治」）：
  1. **同步查询接口不存在**：explorer 逆向 host bundle 穷举全部 `session:`/`task:`/`turn:` handler，**没有** `session:is-streaming`/`session:active`/`session:turn-state`/`session:status` 任何一个。不是权限拦住，是宿主压根没注册。宿主内核有权威判定 `isSessionStreaming(t)`（bundle 行 28865-28866，靠 `_prePromptAbortControllers` Map + `session.isStreaming`），但未挂到插件 bus，插件够不到。
  2. **`bus.subscribe` 能注册但收不到事件**：probe 实测 `bus type=object, subscribe type=function`，订阅 `session_status`/`turn_start`/`turn_end`/`message_end` 全部 ok 不报错。但整轮对话（含发起下载/收消息）**零条 BUS-EVENT**——宿主不把这些 turn/session 事件转发给插件总线。`subscribe` 是「看起来能用、实则收不到」的空壳。
  3. **与坑9方案Y闭环**：v0.6.2 订阅 turn 事件 0 命中；本次 session_status 同样 0 命中。两次实测一致坐实：宿主架构就不让插件碰 turn/回合级状态。
- 结论：**插件拿不到任何「当前回合是否活跃」的信号**。2秒窗口竞态在纯插件侧**无法根治**。它应被定性为「已知的、无害的、偶尔一条的边缘冗余」——方向是「多」不是「漏」，量级远小于坑9的「批量 10 条灾难」。投递本身不坏（agent 收束前没拿到，投递是对的）；坏的是「wait 已拿到仍再投一条」。
- 教训：
  6. **「赌时间窗口」的机制天生不可靠**：用一个固定秒数去赌「另一个异步动作赶不赶上」，输赢靠运气（网络/调度延迟），代码逻辑无关。凡是要靠「等窗口」来区分两种时序的，本质是猜，必有漏网之鱼。
  7. **共享宿主事件订阅是有欺骗性的接口**：`bus.subscribe` 接口存在、能注册、不抛错，但宿主根本不会把 turn/session 状态事件喂给插件。逆向时「有这个方法」≠「这方法会触发」，必须实测回调计数，不能只看 API 存在。
  8. **判断该不该修复，要看「重复的无害性」和「修复的成本/风险」**：边缘偶发一条（无害）vs 动宿主内核/维护事件状态机（高成本+已实测撞墙）→ 接受它，把资源留给真正批量的病（坑9已修）。
  9. **宿主内核自嗨的判定方法**：宿主 bundle 里 grep 到 `isSessionStreaming` 等逻辑 ≠ 插件可用。要看它是否被 `e.handle("...")` 注册成插件可 `bus.request` 的 handler，以及 `session:get` 等返回字段是否含运行期状态。方法名在 bundle 里出现 ≠ 暴露给插件。
- 版本线：v0.6.4（后注册，修批量重复，保留）→ v0.6.5（本次 probe，仅实测用，已清理）。插件生产代码保持 v0.6.4，2秒窗口竞态作为已知限制接受。

### 坑11：「回合收束自动补注册」破解"agent忘调wait漏通知"——关键突破 + fs.watch失灵坑（v0.6.5）
- 结论先行：**v0.6.5 用「插件轮询 jsonl size 检测回合收束写入」解决了宿主动态，补上了 agent 收束前忘调 wait 导致的漏通知。** 这是整个下载通知链路最重要的突破。
- 核心洞察（用户提的）：**"先结束才有写入"**——宿主不暴露 turn 状态给插件（坑10已证实），但宿主**必然**把回合状态写进会话 jsonl，且回合收束（agent 这一轮做完、停下等下一步）时留下 **`assistant(stopReason=stop)` 的定格写入**。这个写入是外部（插件）能读到的、恒真实的收束信号。
- 机制：插件 onload 起一个轮询器（150ms），对"未完成+占位未注册"任务的 sessionPath jsonl 做 stat size 轮询；检测到收束写入瞬间，对该会话下所有"未完成+占位未注册"任务**补注册** `deferred:register`。任务终态后正常 `deferred:resolve` 自动投递唤醒。
- 实测（两次铁证）：发起下载**不回wait** → agent收束 → 任务完成 → **自动投递** `hana-background-result`（taskId 645dfa6c / 8ab96e2c，宿主 deferred-tasks.json 占位 status=resolved 且唯一，无重复）。
- 关键教训：
  10. **fs.watch 对宿主 jsonl 失灵，改用「轮询 stat size」100% 可靠**：Node `fs.watch` 注册成功但**完全无法触发**（实测 watch jsonl 文件 5 秒 0 fire，即使文件持续写入）。宿主写入 jsonl 的方式（mmap/缓冲/特殊 fd）让 ReadDirectoryChangesW 感知不到。而 **jsonl 是只增不减的**，用 `fs.statSync().size` 轮询增量必然可靠。这是本次最值钱的一条：**凡是对宿主进程正在写的文件做"变化感知"，fs.watch 可能失灵，轮询 size（或 mtime）才稳。**
  11. **宿主把 turn/session 状态"关在内部"，但"必然落盘的 jsonl"是插件够得着的白盒**：挖宿主接口（bus.subscribe/turn事件/session查询）全部撞墙（坑10），但宿主的 jsonl 是它"必然写、插件能读"的恒真实状态源。**遇到"拿不到宿主动态状态"的问题，优先想"宿主会把什么必然落盘"**，而不是死磕它的 RPC 接口。
  12. **「收束瞬间」是catch时机，不是靠轮询到它**：用轮询 size 增量捕捉收束写入，关键在"写入那一刻"就判收束（tailSettled 读最近一条是否 assistant+stop），而不是"等一段时间后看有没有活动"（那是时间阈值，又会回到坑10的猜）。事件驱动或极短轮询，才能抓住"瞬间态"。
- 备选方案存档：`tools/dl-recon.js` 是"独立侦察进程"版（脚本读 jsonl 收束 + 写标记给插件），与插件内轮询等价，留作可扩展。主方案用插件内轮询（链路短、不跨进程）。
- 防重复设计：只补 `deferredRegistered !== true` 任务；补注册用 `manager.getTask()` 取原始引用（`list()` 返回 snapshot 拷贝，改拷贝不回写）。host 侧占位注册成功即"唯一投递"。
- 版本线：v0.6.4（后注册，修批量重复）→ v0.6.5（回合收束自动补注册，堵漏通知）。两者共同形成：**批量不重复（v0.6.4）+ 单任务不漏（v0.6.5）**。剩余边缘冗余（2秒窗口竞态，坑10）定性为已知无害。

### 坑12：跨会话投递——dl-nextturn 全局监听 fan-out，sessionId 格式差异（v0.7.2）
- 现象（2026-08-27 用户反馈）：下载完成通知出现在非创建它的会话。delivered via nextTurn by plugin 理由串泄漏为可见消息。
- 根因（explorer 源码级确认）：
  1. **dl-nextturn 扩展是 per-session 加载**（Hana Pi extensions 在每个 AgentSession 各加载一次），每个实例都读 globalThis.__dlTaskMgr（进程级单例，跨 session 共享）。
  2. dlcore._finalWaiters 是**进程级 Map**（	askId → waiter Set），fan-out 到所有 session 的扩展 waiter。
  3. 每个扩展都 pi.sendMessage 到**自己 session 的 runtime**（per-session 队列天然隔离）→ 消息出现在 N 个会话。
  4. **结论**：投递本身（nextTurn per-session / deferred 按 sessionPath）天然按 session 隔离，bug 只源于「扩展全局监听所有任务 + 每个 session 都 fire」。
- **sessionId 格式差异**（probe-events 实测揭示的关键陷阱）：
  - ctx.sessionManager.getSessionId() 返回**内部 session id**（如  1a04436-fd17-7e50-98c6-dc30b8fdee8e）
  - 	ask.sessionId 是**外部 sess_ 格式**（如 sess_0mtbs8ggy_995bb8935d0679d49d64）
  - 两者**不是同一字段**，**不可用 sessionId 比较**
  - **sessionPath（jsonl 文件名）两端一致**（扩展 getSessionFile() = …/<uuid>.jsonl，task.sessionPath 同路径），故用 sessionPath 匹配最可靠
- **session 标识拿取通路**（probe-events 实测）：
  - HFt facade 不暴露 sessionManager，唯一通路是 pi.on("事件名", (_, ctx) => ctx.sessionManager.getSessionId/getSessionFile)
  - 可用事件：	ool_execution_start / 	ool_execution_end / 	urn_start / session_start / gent_start 等
  - session_start 可能错过（扩展加载晚于 session 启动），但 	ool_execution_*/	urn_start 必然在 session 活跃时触发 → 用它们兜底抓
- **修复**（v0.7.2，commit 9ad8fc5）：
  - xtensions/dl-nextturn.js 加 captureSession(ctx) 从事件 ctx 抓 currentSessionPath = ctx.sessionManager.getSessionFile()
  - ownThisSession(task) 按 sessionPath 归一化文件名匹配（String(p).split(/[\\/]/).pop() 取尾部 jsonl 文件名）
  - 不匹配 → 静默（防跨会话 fan-out 兜底）
  - 兼容：currentSessionId 仅 path 缺失时兜底（且加 sess_ 前缀容错）
- **suppress reason 泄漏处理**：v0.7.1 加的宿主 deferred:suppress RPC 补丁，suppress 后 reason 串变成了可见消息。**已回退宿主 bundle 补丁**（index.js.bak-before-suppress 恢复），撤销插件侧 suppress 调用，回到干净的 nextTurn+deferred 单通道分界。
- **教训**：
  13. **per-session 加载的扩展如果读进程级全局单例，必有 fan-out 风险**：任何被多 session 共享的对象（TaskManager / EventBus / 进程级 Map）都是"跨会话污染"的源头。扩展要么不读全局，要么必须按 session 过滤。
  14. **同一概念的两个 id 体系不要混用**：宿主内部 session id（uuid）和外部 sessionId（sess_<uuid>）是**两种不同字段**，外部 API 暴露时容易让人以为是同一个。比较前必须先确认两边的字段语义。
  15. **sessionPath 是最可靠的 session 归属标识**：因为它直接指向会话 jsonl 文件，宿主和插件都看得到，而 sessionId 在内部/外部可能用不同格式。判断"任务属于哪个 session"优先用 sessionPath。
  16. **「宿主接口存在」不等于「宿主事件会触发」**（坑10教训）：HFt facade 上 vents 看起来能订阅，但 session 生命周期事件需要走 pi.on(...)（不是 pi.events）。plugin extensions 是另一条总线机制。
  17. **诊断优先于猜测**：扩展能收到哪些事件、ctx 含什么字段，需要 probe-events 一次性看清，而不是反复猜"是不是这个事件"。

- **教训**：
  18. **「fail-open 放行 ≠ 过滤生效」**：两者观察现象相同（任务正常投递），但前者是『没拦住』，后者是『拦住了非本会话』。验证必须看到『非本会话任务被拦截』的日志（如 wire-skip）才算真生效，单看到『本会话任务正常投递』不能证明。
